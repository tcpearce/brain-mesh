# Brain mesh: batch ingest with agents

Read `brain-mesh`, its FORMATS.md and `brain-mesh-add-paper` first. Each agent follows add-paper steps 2 to 7 for its own paper; this document adds the division of labour that lets several agents work on one vault at once.

With up to about five papers, add them one at a time with `brain-mesh-add-paper`. Beyond that one session runs out of room long before it runs out of papers. A 9-page paper's main text came to about 60 cards in the first test, so 50 papers is several thousand cards.

## Why three phases

Each paper's own folder (`sources/P012-<slug>/`) can be written by one agent without touching anyone else's. Everything shared cannot be: concept hubs, findings, tensions, gaps, `index/`, `MAP.md`, the ledger and the marked PDFs. So:

1. **Prepare** (one session, in order): register every paper and seed the shared vocabulary.
2. **Extract** (one agent per paper, in parallel): each writes only its own folder.
3. **Merge** (one session, in order): merge proposed concepts, rebuild, link across papers, integrate.

## Cost, before anything starts

Agents multiply token use. One unplanned fan-out of agents has already used up a whole week's token limit. So before launching:

- Tell the user how many papers, how many agents, how many batches, and an estimate of the tokens: extract the first paper in this session, note what it used, and multiply. Ask the user to confirm.
- Run 5 to 8 agents per batch, not all papers at once. Ask again before each batch unless the user approved the whole run. Once the user has asked for the papers to be carded, carry every registered paper through extraction, merge and integration without stopping between batches, and keep working on the merge while agents run; stop only for a decision that is the user's.
- Agents run in the background. Do not poll them; their reports arrive when they finish.

## Phase 1: prepare

1. **Gather.** The user puts the papers and their supplementary files in the vault's `ingest/` folder, which git ignores; large ones are linked, not committed, when anchored (`brain-mesh-setup`, **Large files are linked**). List the papers. For each, do add-paper step 0: find its supplementary material and released data. Ask the user once for everything missing across all papers, naming each item, and for any paper they want treated as high or low priority (suggest high for papers rich in high-priority concepts or bearing on research gaps).
2. **Register.** Allocate source ids here and nowhere else, in order (`python3 tools/mesh.py id P`), so no two agents take the same id. Anchor each paper (`anchor P012 file.pdf`, and `anchor P012 --si <files>` for its supplementary material). Write a minimal source card for each: title, authors, year, venue, DOI and a `coverage::` line per unit, including the supplementary material. The extraction agent completes its study profile (`question::`, `design::`, `sample::`, `framework::`). Then, for each paper in order, `refs P012` and `cite P012`, so the reference cards exist before the agents start and their cards can carry `cites::` lines. The agents check `P012_refs.md` against the paper; the merge runs `cite` again, which fills in what they found. A list `refs` cannot read (author-year style) is written by the agent, and its `cites::` lines are added at the merge. List every unit in the coverage lines, including those publishers put beside the supplement: Extended Data figures and tables (part of the main PDF), the reporting summary, a peer-review file and source-data files.
3. **Seed the vocabulary.** Start from the high-priority concepts. Read every abstract, and the introduction of the two or three most central papers. Propose the concepts that will recur across papers (`propose ... `, without `--from`): the main variables (with units), methods, materials, phenomena and categorical variables, each with its aliases. Show the user the list in one message and adopt what they approve before the agents start. A shared starting vocabulary is what stops ten agents inventing ten names for one thing. Whatever the topic, make sure the vault has the two condition variables every card's `when::` lines need: `species` (categorical: the organism, or human subjects) and `preparation` (categorical: in vivo, ex vivo tissue, slice, dissociated cells, heterologous cells, in silico). Propose them if they are missing, or agents will each invent them.
4. **Build and commit.** `python3 tools/mesh.py build` must end with 0 errors. If the vault is a git repository, commit, so each agent starts from the same state.
5. **Write one brief per agent** from the template below, and run the papers in priority order: each high-priority paper gets its own agent and, once it reports, an independent verifying agent that checks a sample of its cards against the pages; low-priority papers may share an agent with a brief that allows skimming background and discussion. Brief the verifying agents from **The verifying agent's brief** below.

## Phase 2: extract

### The agent brief

Give each agent, in its prompt:

- The vault's path, its paper's id and title, and where the clone of `tcpearce/brain-mesh` is (or how to get it).
- "Work directly: do not start agents or forks of your own." And a scratch folder of its own, outside the vault (`<session scratch>/P012/`), for any script or download: agents that share one scratch folder overwrite each other's files.
- "Read `skills/brain-mesh/SKILL.md`, then `skills/brain-mesh-add-paper/SKILL.md`. Carry out steps 2 to 7 for P012 only. Step 8 (integration) is done later by the session that launched you."
- **May write only** inside its own source folder (`sources/P012-<slug>/`, or `sources/P012/` before its source card exists): its evidence cards, figure files (`P012-F2.webp`, `P012-F2.csv`), `P012_refs.md`, `P012-claims.md`, `P012_concepts.md`, `P012_scan.md` and `P012_progress.md`.
- **Must not write** `concepts/`, `findings/`, `tensions/`, `gaps/`, `hypotheses/`, `experiments/`, `index/`, `MAP.md`, `ledger/`, or another source's folder. Must not run `build`, `mark`, `log`, `anchor`, `seal`, `upgrade`, `sync` or `remove`, which write shared files or the repository.
- **May run** `check P012`, `unread P012`, `sample P012`, `progress P012`, `figure P012 ...`, `refs P012`, `mentions P012`, `claims P012`, `id P012`, `find`, `show`, `concept`, `propose ... --from P012`, `scan P012`, `neighbours P012`, and `split` for batches that hold only its own evidence cards. Must not run `cite`, which allocates reference ids shared by every paper.
- **References.** Run `refs P012` and check `P012_refs.md` as add-paper step 1 says, filling in missing titles and DOIs from records it can look up. Where `refs` cannot read the list, the agent writes `P012_refs.md` by hand in the same format and its cards cite by number (`- cites:: ref 12 — what it supports`); `cite` links them at the merge. List in the progress note every reference card made at registration whose fields are wrong: `cite P012 --update` applies the checked list at the merge.
- **Data sets and code.** Run `mentions P012` and list in the progress note every data set and code base the paper uses, with its name, link or accession, licence if stated, and the cards that rest on it. Do not write data-set or code cards: their ids are shared.
- **Claims.** Draft `P012-claims.md` (`claims P012`) with the main claim and up to five sub-claims linked to its own evidence, writing `no finding yet` where a finding would go; the merging session links the findings.
- **New concepts.** Look first with `python3 tools/mesh.py concept "<name>"`. It shows the existing concepts, the concepts other agents in this batch have proposed so far (marked PROPOSED) and names the user has turned down (REJECTED). If an existing concept fits, link it. If another paper's proposal fits, link to that exact name and do not propose it again. Only if nothing fits, propose it: `python3 tools/mesh.py propose <slug> "<one-sentence definition>" --from P012 [--kind variable --unit 1] [--alias "other name"]`, and link the proposed name from the cards as usual. Search again before each new proposal: other agents keep adding theirs. Links to proposed names are warnings, not errors. Never put concept blocks in a batch for `split`.
- **Propose sparingly.** A concept earns a card when the brain needs a shared word for it: it is central to the paper's argument, or likely to recur in other papers. Technical detail of one method (instrument settings, force fields, bond types, an index used by one paper) stays in the card's prose, linked to the nearest existing concept. More than about 15 proposals for one paper means the bar is too low: the merging session and the user must judge every one.
- **Anchors in Extended Data.** Extended Data figures and tables belong to the main PDF: anchor them with the page (`F6a, p32`), since they share numbers with the main figures. `SI-F6a` points into the supplementary PDF, which may be another document altogether, such as a peer-review file.
- **Citations.** Give every card the works the paper cites for its statement (`- cites:: [[R0042]] — what it supports`), or `- cites:: none — <why>` where the paragraph's citations support another sentence; the paper's own measured or derived results need none.
- **Concept scan.** Once the paper is carded, run `scan P012` and work through it as `brain-mesh-concept-scan` says: card each new fact about an existing concept, add a repeated passage to the card that already states it, or write why there is nothing new on the concept's `decided::` line.
- **Vault rules.** Read the vault's `CLAUDE.md`, including the rules the user set below its generated part, and follow them within these limits. Where a rule asks for a shared change, propose it in your own files: a concept the rules say must be low priority is proposed with `--low "<the rule's reason>"`, and the merging session adopts it as such. Never run `sync`, `build` or `priority`: `CLAUDE.md` exempts extraction agents from its sync rule.
- **Contradictions.** Where a card of the paper cannot hold together with a card of a paper already integrated, or with a hub's facts, link it `contradicts::` with the reason and list it in the progress note. The merging session logs it on the register (`ledger/` is shared).
- **Links to other papers.** Typed links with reasons are welcome from its own cards to cards of papers already integrated. Never edit another paper's cards. Write a card before linking to it from another of its own cards: a link to an id not yet written blocks `build` if the agent stops in between. Candidate links to papers in the same batch go in the progress note.
- **Handover for the merge.** In `P012_progress.md`, under these headings, list what the merging session must write in shared files, one item per line in the form given, so that `mesh.py handover` can apply it: `## Hub facts` (`- [[concept]] :: <fact> — [[P012-031]]`; the works the card cites are added from its `cites::` lines), `## Key figures` (`- [[concept]] :: ![[P012-F2c.webp]] <what it shows> — [[P012-031]]`), `## Links to papers in this batch` (`- [[P012-031]] <relation> [[P013-007]] — <reason>`, the relation one of `supports`, `contradicts`, `replicates`, `extends`, `qualifies`, `underlies`), `## Contradictions` (`- [[P012-031]] ~ [[P006-018]] — <the clash in one sentence>`), and, for the merging session to read, `## Concepts proposed` and `## Condition values missing` (a variable the paper fixes but does not state). Write `- none` under a heading with nothing.
- **Progress note.** After each section of the paper, append to `P012_progress.md`: the date, the section done, the last card id, and anything open (figures still to read, flags, questions for the user). A resumed agent starts with `python3 tools/mesh.py progress P012` and then reads the note.
- **Finish** when `check P012` shows no errors and no warnings other than proposed concepts and the `'cites:: ref N' lines are not linked yet` line (pending until the merge runs `cite`), and `scan P012` has nothing left to do. **Report back in at most ten lines:** cards by type, proposed concepts, flagged cards, `missing::` lines, figures read, and suggested links to other papers.

### While the agents run

The launching session runs no `build`, `mark`, `sync` or `upgrade` until every agent has reported: `build` rewrites the generated block of source cards the agents are editing, and `sync` pushes half-written cards. If shared files must be committed meanwhile (a tooling upgrade, linked files), commit them by path, not with `git add -A`. Ask the user to pause Obsidian Git's automatic commit-and-sync for the same reason.

### The verifying agent's brief

Once the extraction agent of a high-priority paper reports, start a fresh agent that did not write the cards. Give it the vault's path, the paper, and add-paper step 7. It checks every observation and model card and a random sample of 20 others (`sample P012 20`) against the pages viewed as images, the tables and the released data; recomputes independently every value the extractor derived (`origin:: claude`, `status: derived`); compares the equations with their crops (`latex`); and reads `unread P012` for missed statements. It may write only in the paper's folder: it corrects cards in place, keeping their ids, with `- corrected:: <date> verification — <what changed>`; corrects `P012_refs.md` and the figure data files (`P012-F2.csv`) when they are wrong; cards what was missed; adds `flag::` where unsure; and adds a `pass::` line to the source card and a `## Verification` section to the progress note. It runs none of the commands an extraction agent may not, and no `propose`. Report in at most eight lines: cards checked, recomputations against the extractor's, corrections, new cards, flags and a verdict.

### Working copies

If the vault is a git repository and agents can be given their own worktree, give each one its own. They touch only their own folders, so merging the branches back is clean. Otherwise all agents work in the same folder under the rules above.

### When an agent stops

Launch a new agent with the same brief plus "Resume: run `progress P012` first and continue from the progress note." Never run two agents on the same paper at once. An agent stopped by a usage limit keeps its context: where the session can message it (SendMessage), tell it to continue rather than starting a new one.

## Phase 3: merge

1. **Concepts.** `python3 tools/mesh.py staged` lists every proposed concept, which papers propose it, the existing concepts it resembles and its likely twins from other agents.
   - Fold twins and near matches yourself: `python3 tools/mesh.py adopt <name> into <concept or other proposal>` adds its names as aliases and rewrites every link to it in every paper's cards. Into another proposal, the target stays a proposal. Do the twins first, so each idea ends with one name.
   - The rest are new concepts, and those are the user's call. Show the user the list, one line each (name, definition, papers), and act on their word: `adopt <name>` makes the card (a proposal marked low keeps that level), `adopt --all` makes every proposal that matches nothing, `reject <name> "<why>"` turns one down. A vault rule that tells agents to make a kind of concept (as a rule on generic terms may) counts as the user's word for it. Proposals the user has not answered stay proposals: the cards keep linking them, `check` warns, and the next session asks again.
   - Settle the folds, and adopt what the user approves, before step 5: `neighbours` finds links between papers through the concepts they share.
   - Each new concept may be named in papers from earlier batches: `scan` (no arguments) lists them, and `brain-mesh-concept-scan` cards what they say.
2. **References.** Run `python3 tools/mesh.py cite P012 --update` for each paper in turn, never in parallel: it allocates reference ids, and a work cited by several papers in the batch gets one card. For a paper whose agent wrote its reference list by hand, then run `scan P012` and add the `cites::` lines it lists. `--update` applies each agent's corrections to the reference cards made at registration and merges the duplicates they reveal; cards citing by number (`cites:: ref 12`) are linked.
3. **Data sets and code.** From the agents' notes, make one data-set or code card per data set or code base (several papers often share one), with a `used_by::` line per paper, and add the `uses_data::` and `uses_code::` links to the evidence cards.
4. **Build, then apply the handovers.** `python3 tools/mesh.py build` must end with 0 errors. Then `python3 tools/mesh.py handover --all --apply` writes what the agents handed over: each hub fact into its hub's **What is known** with the evidence card, its source and the works it cites (and the matching `cites::` lines), each key figure under **Key equations and figures**, each link to a paper of the batch on the agent's card, and each contradiction on the register. It recognises what is already applied, so it can run again after more concepts are adopted; items on a concept still proposed wait, and are applied once it is adopted. Read what it reports as unreadable and apply that by hand. `check` will not take a source as `integrated` while its handover has items not yet applied. Build again. This also marks every new PDF and rebuilds the reading queue.
5. **Links across papers.** For each new paper run `python3 tools/mesh.py neighbours P012`. Candidates are ranked by the concepts two cards share, rare concepts weighing most. Read both cards and link with a reason, or decide they are unrelated. Add the links the agents suggested in their reports. Then scan for contradictions across the batch and the brain as add-paper step 6 says (`contradictions P012` for each paper, and reading), and log each real one on the register: papers extracted in parallel have never been read against each other.
6. **Integrate.** The hub facts are in from step 4; read each hub the batch touched and rewrite its lines into one article where they now repeat or overtake each other. Do add-paper step 8 for each paper: update the findings, decide on the gaps, tensions, contradictions and hypotheses each bears on, link the findings into its claims card, update the concept hubs, and set each source to `integrated`. Then run `python3 tools/mesh.py discover --recheck` once for the whole batch and take the changes to the user (`brain-mesh-discover` section 8).
7. **Verify.** Do the spot checks of add-paper step 7 on a sample of each paper's cards. For a vault that decisions will rest on, a fresh agent that did not write the cards does the checking. For high-priority papers the verifying agents of phase 2 have done this; read their reports and act on what they left for the merge.
8. **Close.** First keep the reading queue current, as add-paper step 10 says: index the batch's new reference cards from their abstracts (`literature --unindexed` lists them by paper; `brain-mesh-citation-index`; a long list can be split among agents by reference id, so that no two agents write the same card), and run `python3 tools/mesh.py forward P012 P013 …` for the batch's papers (it needs DOIs and a network; say so if there is none). Papers the agents' reports send you to go on with `queue add <doi> --why "..." --from P012`. Then `python3 tools/mesh.py log "..."`, `gapsdoc`, and `python3 tools/mesh.py sync "<batch>"`; its last line counts what is still unindexed or unsearched. Report the works now cited by several papers in the brain, the cited works left unindexed, and the top of the reading queue: what was suggested, the best of Forward, and the ★ works.

Every concept adopted in the merge has been linked on the indexed abstracts that name it in a title or a claim, and `adopt` lists the sources that name it in passages no card covers: the sweep in `brain-mesh-concept-scan` (**After a batch of adoptions**) works them. `ledger/concept-coverage.md` is the record of what is left, and the last line of `sync` counts it.

Then the next batch: phases 2 and 3 again. The vocabulary that later agents start from now includes every concept merged so far.

**How large a batch.** Phase 3 is done by one session, so the merge, not the extraction, sets the pace: about 5 to 8 papers per batch. Each paper is set to `integrated` as it is done, so a resumed merge session sees where it stopped (`health` lists sources not yet integrated). While a batch runs, pause Obsidian Git's auto commit-and-sync on the user's machine, or give the agents their own worktrees, so half-written cards are not pushed.
